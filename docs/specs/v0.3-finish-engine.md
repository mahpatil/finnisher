# Spec: v0.3 — Finish Engine

**Issue**: n/a
**Status**: Draft
**Date**: 2026-05-27

## Problem

Finnisher tracks sessions well but doesn't help you finish anything. A thread with 8/10 todos done looks the same as one barely started. There is no concept of "done" per thread, no signal for which projects are closest to shipping, no friction when you're about to add your 8th half-finished thing, and no weekly view of whether you actually shipped anything.

## Context

Current state (v0.2.0):
- `threads` has `momentum` and `lastVelocity` schema fields that are computed but never surfaced
- `threadTodos` table exists with done/position tracking
- `blockers` table exists with critical/retrying/resolved status
- `overloadWarning` in `src/db/threads.ts` fires a passive warning when active threads > 5 — but it runs *after* the add, not before
- `isStalled(thread)` already computes staleness at read time (`updatedAt > 48h`)
- No per-thread definition of done, no completion %, no daily/weekly summary

## Implementation Order

Implement in this order — each slice stands on its own and makes the next more useful:

1. **F3** — Abandon Prevention (no schema change, highest UX impact)
2. **F1** — Launch Gate (new `launch_criteria` table; foundation for F2 signal)
3. **F2** — Last 20% Detection (computed field using todos + sessions + blockers + criteria)
4. **F4** — Session Intent (schema addition to `sessions`)
5. **F5** — `finn week` / `finn day` (new CLI command)

## F3 — Abandon Prevention at Add

### Acceptance Criteria

- [ ] Given 2 or more stalled threads (staleness = `updatedAt > stall_hours * ms`, default 48h), when `finn add` is run interactively, then before the title prompt, Finnisher displays a table of up to 5 stalled threads (id, title, last touched, priority) and asks "Any of these closer to done than your new idea?"
- [ ] Given the user selects one of the stalled threads from the prompt, then `finn add` exits and prints `finn next <id> <action>` guidance so the user can refocus on the selected thread (no automatic state change — user must do it)
- [ ] Given the user selects "Proceed with new thread" (always available as the last option), then `finn add` continues normally to the title/nextAction/owner/state prompts
- [ ] Given fewer than 2 stalled threads, when `finn add` is run, then no interrupt prompt is shown — flow proceeds as today
- [ ] Given `finn add --title <t> --next <a>` (non-interactive flags), when run, then no stall check is shown (flag-mode bypasses the friction gate)

### Technical Design

**Data Model Changes**: None.

**Key Logic**:
- Read stall hours from `~/.finnisher/config.json` key `stall_hours` (number). Default: 48. Write a thin `readConfig() / writeConfig()` helper in `src/lib/config.ts`.
- Reuse `isStalled(thread)` from `src/db/threads.ts` — but pass the stall threshold so it's configurable.
- Show at most 5 stalled threads sorted by `updatedAt` ascending (stalest first).
- Use `@clack/prompts` `select` prompt with one option per stalled thread + a "Proceed — add new thread" sentinel.

**Config file shape** (`~/.finnisher/config.json`):
```json
{
  "stall_hours": 48
}
```

### Test Scenarios

**Happy Path**
1. `finn add` with 3 stalled threads → stall interrupt shown → user picks "Proceed" → normal add flow
2. `finn add` with 3 stalled threads → user picks stalled thread → exit with guidance message

**Edge Cases**
1. `finn add` with 1 stalled thread → no interrupt, direct to title prompt
2. `finn add --title foo --next bar` with 5 stalled threads → no interrupt
3. Config file missing `stall_hours` → defaults to 48h without error

**Error Cases**
1. Config file is malformed JSON → silently ignore, use defaults

### Out of Scope
- Automatically updating the selected thread's priority or state
- `finn config set stall_hours N` CLI command (D3, v0.4)
- Configurable focus_limit beyond the existing `overloadWarning` 5-thread threshold

## F1 — Launch Gate (Definition of Done per Thread)

### Acceptance Criteria

- [ ] Given a thread exists, when `finn launch <id>` is run and no criteria exist, then Finnisher prompts "What does shipping this look like?" and lets the user add 1–5 criteria (one per prompt, empty input stops)
- [ ] Given criteria already exist on the thread, when `finn launch <id>` is run, then Finnisher shows current criteria with checkboxes and prompts the user to add more or toggle existing ones
- [ ] Given the user runs `finn launch <id> --check <N>` (1-indexed), then criterion N is toggled (checked ↔ unchecked), `checkedAt` is set or cleared
- [ ] Given all criteria on a thread are checked, when `finn list` is run, then the thread shows a `[READY]` badge in the priority column
- [ ] Given a thread has criteria and all are checked, when `finn done <id>` is run, then it completes normally (no block); if criteria exist but some are unchecked, then it prints a warning "⚠ Launch gate incomplete — N criteria unmet" before closing
- [ ] Given the web dashboard thread detail page, then a "Launch Gate" section appears below Todos showing criteria as checkboxes; clicking a checkbox PATCHes the criterion checked state

### Technical Design

**Data Model Changes**:
New table `launch_criteria`:
```sql
CREATE TABLE launch_criteria (
  id        TEXT    PRIMARY KEY,
  thread_id TEXT    NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  text      TEXT    NOT NULL,
  checked   INTEGER NOT NULL DEFAULT 0,
  position  INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  checked_at  INTEGER
);
```
Add to `src/db/schema.ts` and generate migration `0005_launch_criteria.sql`.

**New DB functions** (`src/db/launchCriteria.ts`):
- `getLaunchCriteria(threadId)` → `LaunchCriterion[]`
- `addLaunchCriterion(threadId, text)` → `LaunchCriterion`
- `toggleLaunchCriterion(id, checked)` → void
- `deleteLaunchCriterion(id)` → void
- `isLaunchReady(threadId)` → boolean (all criteria exist and are checked; returns `false` if no criteria)

**API / Interface Changes**:

| Method | Path | Description |
|--------|------|-------------|
| GET    | /api/threads/[id]/launch-criteria | List criteria for thread |
| POST   | /api/threads/[id]/launch-criteria | Add a criterion `{ text }` |
| PATCH  | /api/threads/[id]/launch-criteria/[critId] | Toggle `{ checked: boolean }` |
| DELETE | /api/threads/[id]/launch-criteria/[critId] | Remove criterion |

REST rules checklist:
- [x] Nouns not verbs in paths
- [x] Correct HTTP verbs
- [x] Status codes: 200/201/204 success · 400 bad input · 404 not found
- [x] Scoped under thread (parent resource)

**CLI**: New `finn launch <id>` command in `src/cli/commands/launch.ts`. Interactive flow uses `@clack/prompts`.

### Test Scenarios

**Happy Path**
1. `finn launch abc` with no criteria → prompts for criteria → 3 added → shows confirmation
2. `finn launch abc` with 2 existing → shows current list → user adds 1 more
3. `finn launch abc --check 1` → criterion 1 toggled to checked
4. All criteria checked → `finn list` shows `[READY]` badge next to thread

**Edge Cases**
1. `finn launch nonexistent` → error "Thread not found"
2. `finn done <id>` with 2/3 criteria checked → warning printed, thread closes anyway
3. Thread with 0 criteria → `isLaunchReady` returns `false`, no `[READY]` badge

**Error Cases**
1. PATCH with invalid `checked` type → 400
2. POST with empty `text` → 400 "text is required"

### Out of Scope
- "SHIP IT" visual state or green launch banner in dashboard (Phase 2)
- `finn launch <id>` deleting / reordering criteria interactively (Phase 2)
- Launch criteria as a required gate blocking `finn done` (design decision: warn only)

## F2 — Last 20% Detection

### Acceptance Criteria

- [ ] Given a thread, `computeCompletionPct(threadId)` returns a float 0–1 using the formula below; the result is never stored — computed at read time
- [ ] Given a GET to `/api/threads`, each thread object includes a `completionPct` field (float 0–1, rounded to 2 decimal places)
- [ ] Given threads with `completionPct >= 0.75` exist, when the web dashboard loads, then a "Sprint Candidates" section appears at the top of the threads list with an amber/gold `[~DONE]` badge on each such thread
- [ ] Given `finn list` is run, then threads with `completionPct >= 0.75` show `[~DONE]` in the state column
- [ ] Given `completionPct < 0.75` for all threads, the "Sprint Candidates" section is hidden (not shown empty)

**Completion Signal formula:**
```
completionPct =
    (todos_done / todos_total) * 0.4          // 0 if no todos
  + (sessions_last_7d >= 3 ? 0.2 : 0)
  + (blockers_open === 0 ? 0.2 : 0)
  + (launch_criteria_met / launch_criteria_total) * 0.2  // 0 if no criteria
```
Note: if `todos_total === 0`, the todos term is 0. If `launch_criteria_total === 0`, the criteria term is 0. Max possible score without todos or criteria = 0.4 (sessions + blockers terms only) — ensures unbounded threads never reach the 0.75 threshold.

### Technical Design

**Data Model Changes**: None (computed at read time).

**New DB function** (`src/db/completionPct.ts`):
```typescript
export function computeCompletionPct(threadId: string): number
```
Queries `threadTodos`, `sessions` (count where `startedAt > now - 7d`), `blockers` (count where `status !== 'resolved'`), `launch_criteria`.

**API Change**: Update `GET /api/threads/route.ts` to include `completionPct` in each thread response. Call `computeCompletionPct(t.id)` for each thread in the list.

**Dashboard**: "Sprint Candidates" card section using amber colour from the existing MUI/design system. Threads already in the list but also shown in the Sprint Candidates section at top.

**CLI**: Update `src/cli/commands/list.ts` — compute `completionPct` for each thread, append `[~DONE]` tag if >= 0.75.

### Test Scenarios

**Happy Path**
1. Thread with 8/10 todos done, 3 sessions last 7d, 0 blockers, 0 criteria → `(0.8*0.4) + 0.2 + 0.2 + 0 = 0.72` — no badge
2. Thread with 10/10 todos done, 3 sessions, 0 blockers, 2/2 criteria met → `0.4+0.2+0.2+0.2 = 1.0` — badge
3. Thread with 0 todos, 0 sessions, 1 open blocker, 0 criteria → `0.0` — no badge
4. `finn list` with 2 sprint candidates → both show `[~DONE]`

**Edge Cases**
1. Thread with no todos, no sessions, no blockers, no criteria → `0.0`
2. Thread with all criteria met but no todos → up to 0.4 max (session + blocker + criteria terms)
3. `completionPct >= 0.75` exactly → badge shown

### Out of Scope
- `completionPct` stored in the DB or updated by a cron job
- Tweaking the formula weights (this is a heuristic; tune in a follow-up spec)
- Separate "Sprint Candidates" page / dedicated view

## F4 — Session Intent

### Acceptance Criteria

- [ ] Given the `sessions` schema, an `intent` text field (nullable) exists after migration
- [ ] Given `finn intent "<text>"` is run with an active open session in the current directory (matched by `projectPath`), then the intent is saved to that session
- [ ] Given no open session matches the current directory, `finn intent` prints "No active session for this directory" and exits 1
- [ ] Given `finn sessions` is run, then an "Intent" column appears in the output table (truncated to 30 chars, `—` if null)
- [ ] Given the web dashboard Sessions tab, then the intent text is shown in the session rows (below or beside cost/tokens)

### Technical Design

**Data Model Changes**:
Add `intent text` column to `sessions` table. Generate migration `0006_session_intent.sql`.

```sql
ALTER TABLE sessions ADD COLUMN intent TEXT;
```

Add to `src/db/schema.ts`:
```typescript
intent: text('intent'),
```

**New DB function** (`src/db/sessions.ts`):
```typescript
export function setSessionIntent(id: string, intent: string): void
export function getOpenSessionForPath(projectPath: string): Session | undefined
```

**New CLI command** (`src/cli/commands/intent.ts`):
```
finn intent "<goal text>"
```
Finds the open session where `projectPath === process.cwd()` and `endedAt IS NULL`. Sets `intent` on it.

**Dashboard**: `GET /api/sessions` already returns session data — add `intent` to the response shape. Update the Sessions UI component to display it.

### Test Scenarios

**Happy Path**
1. Open session exists for cwd → `finn intent "ship the invoice PDF"` → intent saved, confirmation printed
2. `finn sessions` → Intent column shows "ship the invoice PDF" (truncated if long)

**Edge Cases**
1. `finn intent ""` → error "Intent cannot be empty"
2. Multiple open sessions for same path → pick the most recent `startedAt`

**Error Cases**
1. No open session for cwd → prints error, exits 1

### Out of Scope
- Interactive prompt inside hooks at session start (hooks run non-interactively; `finn intent` is the intentional replacement)
- Intent on manually closed/historical sessions

## F5 — `finn week` / `finn day`

### Acceptance Criteria

- [ ] Given `finn week` is run, then output shows: week date range, count of threads closed this week, session count + total hours, total AI cost, todos checked this week, up to 3 threads with highest `completionPct` ("Closest to done"), stalled threads (sorted by staleness), and a 1-line motivational closing line
- [ ] Given `finn week --json` is run, then the same data is output as a JSON object to stdout (no decoration)
- [ ] Given `finn day` is run, then output shows the same structure but scoped to the current calendar day (midnight–now)
- [ ] Given no sessions in the period, then sessions/cost/tokens show `0` — no crash
- [ ] Given no closed threads in the period, then "Shipped" shows `0`

**`finn week` output shape:**
```
  Week of May 19–25, 2026

  Shipped ✓         2 threads closed
  Sessions          14  (47 hrs tracked)
  AI cost           $4.23
  Todos checked     31 / 38

  Closest to done:
    [~DONE] fluicrm — 8/10 todos, last touched 2h ago
    [~DONE] blog-redesign — all criteria met, ready to ship

  Stalled (>48h):
    [STALL] podcast-notes — last touched 6 days ago
    [STALL] advent-of-rust — last touched 12 days ago

  Ship something this week. You're close on fluicrm.
```

### Technical Design

**Data Model Changes**: None.

**New DB functions** (`src/db/summaries.ts`):
- `weekSummary(from: Date, to: Date)` → structured summary object
- `daySummary()` → calls `weekSummary(startOfDay, now)`

These query: `sessions` (by `startedAt` range), `threads` (closed in range), `threadTodos` (completed in range), `launch_criteria`, `computeCompletionPct` per active thread.

**New CLI commands** (`src/cli/commands/week.ts`):
- `finn week [--json]`
- `finn day` — registered as a separate command that delegates to `weekSummary(startOfDay, now)`

**Motivational line logic**: Pick the thread with highest `completionPct >= 0.75`, insert its title: `"Ship something this week. You're close on <title>."` If none, use generic: `"Ship something this week."`.

### Test Scenarios

**Happy Path**
1. Week with 2 closed threads, 14 sessions, $4.23 cost, 31/38 todos → correct formatted output
2. `finn week --json` → valid JSON with same fields
3. `finn day` → scoped to today, 0 sessions → no crash, shows `0`

**Edge Cases**
1. No sessions in week → all numeric fields show `0`, no "Closest to done" section
2. `completionPct` available for active threads → top 3 shown in "Closest to done"
3. Week spans month boundary → correct date range label

**Error Cases**
1. DB not initialised → error "Run `finn setup` first"

### Out of Scope
- `finn week --since <date>` custom date ranges
- Rich ASCII charts or sparklines
- The elaborate D1 `finn day` briefing from v0.4 (that adds FOCUS NOW / CHECK IN sections — this spec adds only the basic `finn day` summary alias)

## Non-Functional Requirements

### Metrics / Observability
This is a local CLI tool with no network telemetry. Hook errors continue to log to `~/.finnisher/hook.log`.

### Performance
- `computeCompletionPct` is called per-thread at list time. At the expected scale (< 100 threads) this is negligible with SQLite.
- `finn week` / `finn day` must complete in < 500ms.

### Security
- Config file `~/.finnisher/config.json`: read/write by current user only. No sensitive data.
- All DB writes use Drizzle ORM parameterised queries — no string concatenation.
- `intent` text is user-supplied, stored as-is (local tool, no injection risk in SQLite queries via Drizzle).

## Open Questions

1. **F1 — Launch criteria interactive toggle**: `finn launch <id> --check <N>` is proposed. Should the interactive `finn launch <id>` flow also let the user check/uncheck in-session, or is `--check` the only toggle path? Recommend: interactive flow shows current list and allows toggling via a `multiselect` prompt.
2. **F2 — Sessions threshold**: Formula uses `sessions_last_7d >= 3`. Is 3 the right threshold, or should it be `> 2`? (Same result, but the spec should be unambiguous.) Recommend: `>= 3` (i.e. 3 or more sessions in last 7 days).
3. **F5 — `finn day` vs D1**: The roadmap describes D1 as a richer daily briefing (FOCUS NOW / CHECK IN sections with ordered priorities). This spec scopes `finn day` as a minimal alias for the day's summary. D1 remains a v0.4 enhancement. Confirm this is the right split.

## Implementation Notes

- **Config helper**: `src/lib/config.ts` — `readConfig(): Config` (reads `~/.finnisher/config.json`, returns defaults if missing/malformed). Keep it synchronous (consistent with DB layer). Single source of truth for all configurable values.
- **Migration files**: Follow naming convention `000N_<slug>.sql` in `src/db/migrations/`. Next up: `0005_launch_criteria.sql` (F1) and `0006_session_intent.sql` (F4).
- **`finn list` changes**: The list command currently uses `cli-table3`. Add a `completionPct` column only when at least one thread has `completionPct >= 0.75` (avoids cluttering normal output).
- **Web API `/api/threads`**: The existing route returns thread data. Add `completionPct` and a `launchReady` boolean to each thread response object. Avoid adding a new round-trip — compute both in the existing handler.
- **Test file locations**: Unit tests in `src/web/app/api/__tests__/` (existing pattern). CLI tests can go in `src/cli/__tests__/` (create if needed). Keep vitest for unit tests, playwright for e2e.
